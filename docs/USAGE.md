## 1. フォルダ構成

```
genesis-demo/
├─ pyproject.toml        依存パッケージの定義（uv が使う）
├─ uv.lock               依存パッケージのバージョン固定
├─ .python-version       使う Python のバージョン（3.12）
├─ examples/             学習を使わないサンプル
│   ├─ franka_pd_control.py   Franka アームを PD 制御で動かす
│   └─ go2_trot.py            Go2 を数式で作った軌道で歩かせる
├─ locomotion/           強化学習（歩行）
│   ├─ go2_env.py / go2_train.py / go2_eval.py   Go2（Genesis 公式サンプル）
│   ├─ g1_env.py  / g1_train.py  / g1_eval.py    G1 の歩行（Unitree 公式の設定を移植）
│   ├─ g1_climb_env.py / g1_climb_train.py / g1_climb_eval.py   G1 の台へのよじ登り
│   └─ g1_ladder_env.py / g1_ladder_train.py / g1_ladder_eval.py   G1 のはしご登り
├─ assets/unitree_g1/    G1 のモデル（12 関節版・23 関節版の URDF、形状ファイル、ライセンス）
├─ docs/                 ドキュメント（このファイルなど）
├─ logs/                 学習結果（自動で作られる。Git には含めない）
└─ videos/               録画した動画（自動で作られる。Git には含めない）
```

Franka と Go2 のモデルは Genesis に同梱されているものを使うので、assets には G1 だけを置いています。

## 2. 環境構築（新しい PC で再現するとき）

### 必要なもの

| 項目 | この PC での構成 | 備考 |
|---|---|---|
| OS | Windows 11 | |
| GPU | NVIDIA GeForce RTX 4080 Laptop（12 GB） | 強化学習には NVIDIA の GPU がほぼ必須 |
| NVIDIA ドライバー | 596.08（CUDA 13.2 まで対応） | `nvidia-smi` で確認 |
| uv | — | Python と依存パッケージの管理に使う |

Python 本体は uv が自動で用意するので、別途インストールする必要はありません。

### 手順

```powershell
# 1. uv をインストール（未導入の場合。インストール後は PowerShell を開き直す）
winget install --id=astral-sh.uv -e

# 2. リポジトリを取得して、そのフォルダに移動
git clone https://github.com/tmsy-temp/genesis-demo.git
cd genesis-demo

# 3. 依存パッケージを一括インストール（uv.lock のとおりのバージョンが入る）
uv sync

# 4. 動作確認
uv run python -c "import torch; print(torch.__version__, torch.cuda.is_available())"
uv run python -c "import genesis as gs; gs.init(backend=gs.gpu); print('OK')"
```

4 の 1 行目で `True` と出れば PyTorch が GPU を認識しています。2 行目でログの後に `OK` と出れば、Genesis も GPU で動きます。

### 依存パッケージ

| パッケージ | 用途 |
|---|---|
| genesis-world | 物理シミュレーター本体（1.4.5 で動作確認） |
| torch | PyTorch。**CUDA 13.0 版（cu130）** を PyTorch 公式の配布元から取得する設定 |
| rsl-rl-lib | 強化学習ライブラリ（PPO）。5.0.0 以上が必要 |
| tensorboard | 学習の経過をグラフで見るツール |
| numpy | 数値計算 |

PyTorch の取得先は `pyproject.toml` の `[[tool.uv.index]]` で cu130 版に固定しています。
古いドライバーで CUDA 13 に対応していない PC では、この URL を `https://download.pytorch.org/whl/cu126` などに変えてから `uv sync` し直してください。

パッケージを追加するときは `uv add <パッケージ名>` を使います（`pyproject.toml` と `uv.lock` が自動で更新されます）。

## 3. 共通の注意点

- **必ず genesis-demo フォルダで実行する**：学習結果の保存先（`logs/`）や録画の保存先（`videos/`）は、実行したフォルダからの相対パスで決まります。
- **`uv run` を付けて実行する**：仮想環境（`.venv`）を有効化（Activate）する手順は不要です。
- **初回は起動が遅い**：Genesis は最初の実行時に物理計算のプログラム（カーネル）をコンパイルするため、ビューアーが出るまで数十秒〜1 分ほどかかります。2 回目以降はキャッシュが効いて速くなります。
- **途中で止めるとき**：ビューアーのウィンドウを閉じるか、PowerShell で Ctrl+C を押します。
- **無視してよい警告**：

  | 警告 | 出る場面 | 理由 |
  |---|---|---|
  | `Neutral robot position (qpos0) exceeds joint limits.` | Go2 の読み込み時 | 全関節 0 度の姿勢が膝の可動範囲外なだけ。実際の姿勢は範囲内 |
  | `Mesh is not watertight` / `dubious inertia` / `dubious mass` | G1 の読み込み時 | Unitree の URDF の質量・慣性の値が形状からの推定と違うだけ。Unitree 自身が使っている値なのでそのまま使う |

## 4. ロボットごとの使い方

### 4.1 Franka アーム：PD 制御のサンプル

ロボットアームを 4 つの姿勢に順番に動かす、一番シンプルなサンプルです。学習は使いません。

```powershell
uv run python examples/franka_pd_control.py                # 2 周して終了
uv run python examples/franka_pd_control.py --cycles 10    # 10 周させる
```

| オプション | 意味 |
|---|---|
| `--cycles N` | 姿勢の巡回を何周するか（既定 2） |
| `--cpu` | CPU で実行する |
| `--no-viewer` | ビューアーを表示しない |

### 4.2 Go2（4 足）：数式による歩行

足先の軌道を数式で作り、逆運動学で関節角度に変換して歩かせるサンプルです。学習は使いません。
姿勢のフィードバックがないので、歩幅や周期を大きくしすぎると転倒します。

```powershell
uv run python examples/go2_trot.py                       # 20 秒歩く
uv run python examples/go2_trot.py --step-length 0.16    # 歩幅を広げる
```

| オプション | 意味 |
|---|---|
| `--duration 秒` | 歩く時間（既定 20） |
| `--step-length m` | 歩幅（既定 0.12） |
| `--step-height m` | 足を持ち上げる高さ（既定 0.06） |
| `--period 秒` | 1 歩行周期の時間（既定 0.4） |
| `--cpu` / `--no-viewer` | CPU で実行 / ビューアーなし |

### 4.3 Go2（4 足）：強化学習

Genesis 公式のサンプルをそのまま取り込んだものです。前方に 0.5 m/s で歩くことだけを学習します。

**学習**

```powershell
uv run python locomotion/go2_train.py
```

| オプション | 意味 |
|---|---|
| `-e 名前` | 実験名。`logs/<名前>/` に保存される（既定 `go2-walking`） |
| `-b 数` | 並列に動かすロボットの数（既定 4096） |
| `--max-iterations 数` | 学習のイテレーション数（既定 101） |
| `--seed 数` | 乱数のシード（既定 1） |

**再生**

```powershell
uv run python locomotion/go2_eval.py --ckpt 100
```

| オプション | 意味 |
|---|---|
| `-e 名前` | 実験名（既定 `go2-walking`） |
| `--ckpt 数` | 読み込むチェックポイントの番号（既定 100。101 イテレーション学習したときの最後の番号） |

### 4.4 G1（ヒューマノイド）：強化学習

Unitree 公式の学習コード（unitree_rl_gym）の G1 の設定を Genesis 向けに移植したものです。
脚の 12 関節だけを動かし、前後・左右・旋回の速度指令に従って歩くことを学習します。

**学習**

```powershell
# 新しく学習する（4096 体 × 1000 イテレーション）
uv run python locomotion/g1_train.py

# 学習の続きをする（model_999.pt から、さらに 2000 イテレーション）
uv run python locomotion/g1_train.py --resume 999 --max-iterations 2000
```

| オプション | 意味 |
|---|---|
| `-e 名前` | 実験名。`logs/<名前>/` に保存される（既定 `g1-walking`） |
| `-b 数` | 並列に動かすロボットの数（既定 4096） |
| `--max-iterations 数` | 学習のイテレーション数（既定 1000） |
| `--resume 番号` | そのチェックポイントから学習を再開する。設定は前回の `cfgs.pkl` を使う |
| `--seed 数` | 乱数のシード（既定 1） |
| `--cpu` | CPU で実行する（動作確認用。学習には GPU が必要） |

**再生**

```powershell
uv run python locomotion/g1_eval.py                    # 最新のチェックポイントを再生
uv run python locomotion/g1_eval.py --ckpt 999         # 番号を指定して再生
uv run python locomotion/g1_eval.py --vx 0.8           # 最初の前進速度を 0.8 m/s にする
```

ビューアーは **G1 が止まった状態で開きます**。ウィンドウをクリックしてから **Enter** を押すと歩き始めます。

| オプション | 意味 |
|---|---|
| `-e 名前` | 実験名（既定 `g1-walking`） |
| `--ckpt 番号` | 読み込むチェックポイント（省略時は最新） |
| `--vx` / `--vy` / `--wz` | 最初の速度指令：前後 [m/s]・左右 [m/s]・旋回 [rad/s]（既定 0.5 / 0 / 0） |
| `--no-wait` | Enter を待たずにすぐ歩き始める |
| `--no-heading-hold` | 向きを保つ自動補正を無効にする（下記参照） |
| `--no-viewer` | ビューアーなしで `--duration` 秒だけ動かし、結果を表示する |
| `--duration 秒` | `--no-viewer` のときに動かす時間（既定 10） |
| `--record [ファイル名]` | 動画に録画する（[7. 録画](#7-録画) 参照） |
| `--record-res 幅x高さ` | 録画の解像度（既定 1280x720） |

再生中のキー操作（ビューアーのウィンドウを選択した状態で押す）：

| キー | 動作 |
|---|---|
| Enter | 歩行の開始・一時停止 |
| Backspace | 初期位置に戻して一時停止（撮り直し用） |
| ↑ / ↓ | 前後の速度を 0.1 m/s ずつ変える |
| ← / → | 旋回の速度を 0.1 rad/s ずつ変える（← が左旋回） |
| `,` / `.` | 左右の速度を 0.1 m/s ずつ変える（`,` が左） |
| Space | 停止（全ての速度指令を 0 にする） |

速度指令は、学習した範囲（前後 −0.5〜1.0 m/s、左右 −0.3〜0.3 m/s、旋回 −0.5〜0.5 rad/s）に自動で収められます。

**向きの自動補正について**

方策が従っているのは「旋回速度」の指令だけで、向きそのものは見ていません。そのため旋回速度 0 の指令でも、わずかな誤差が積み重なって少しずつ曲がっていきます。
再生スクリプトでは、旋回の指令が 0 のあいだ、歩き始めた向き（または最後に旋回し終えた向き）とのずれに応じて旋回速度の指令を自動で補正し、まっすぐ歩かせています。

**性能を数字で確かめる**

```powershell
uv run python locomotion/g1_eval.py --ckpt 999 --no-viewer --duration 20
```

終了時に「最終位置・向き・平均速度・転倒回数」が表示されます。
平均速度は「スタート地点から最終位置までの直線距離 ÷ 時間」なので、まっすぐ歩くときだけ意味があります。旋回を含む場合は、[8. これまでの結果の記録](#8-これまでの結果の記録) のように、理想の円軌道の最終位置・向きと比べます。

### 4.5 G1（ヒューマノイド）：台へのよじ登り

腕のある 23 関節版の G1 が、正面の台に手足を使って登り、台の上に立つことを学習します。参照動作は使わず、報酬設計とカリキュラムだけで学習します。

**学習**

```powershell
uv run python locomotion/g1_climb_train.py                                    # 4096 体 × 3000 イテレーション
uv run python locomotion/g1_climb_train.py --resume 2999 --max-iterations 1000  # 続きを学習する
```

オプションは G1 の歩行と同じです。既定の実験名は `g1-climb-v9a` で、再生スクリプトも同じ名前を既定で読みます。v5 以降は `--replay locomotion/climb_start_states.pt` を付けて学習します（下記「途中の姿勢から始める」参照）。以前の版を再生するときは `-e g1-climb-v5` などを付けます。

```powershell
uv run python locomotion/g1_climb_train.py -e g1-climb-v7 --replay locomotion/climb_start_states.pt   # v7 の学習（最初から）
uv run python locomotion/g1_climb_train.py --init-from g1-climb-v7:2999 --max-iterations 1000 --replay locomotion/climb_start_states.pt
                                                                              # v8b の学習（v7 の学習済みモデルから始める）
uv run python locomotion/g1_climb_train.py -e g1-climb-v9a --init-from g1-climb-v8b:3998 --max-iterations 1000 --replay locomotion/climb_start_states.pt
uv run python locomotion/g1_climb_train.py -e g1-climb-v9b --height-max 1.2 --init-from g1-climb-v8b:3998 --max-iterations 1000 --replay locomotion/climb_start_states.pt
                                                                              # v9a・v9b の学習（v8b の学習済みモデルから始める）
```

**再生・評価**

```powershell
uv run python locomotion/g1_climb_eval.py                          # 最新のチェックポイントで、高さ 0.6 m の台に挑戦
uv run python locomotion/g1_climb_eval.py --height 0.4             # 台の高さを変える
uv run python locomotion/g1_climb_eval.py --no-viewer --trials 20 --height 0.4   # 画面なしで 20 回挑戦し、成功率を表示
uv run python locomotion/g1_climb_eval.py --record --height 0.6    # 録画する
```

1 回の挑戦は最大 10 秒で、転倒するか 10 秒たつと自動で台の手前に戻って次の挑戦を始めます。ビューアーでのキー操作は Enter（開始・一時停止）と Backspace（台の手前に戻す）です。

**学習の仕組み（要点）**

- **進み具合の報酬**（v4）：到達度（0〜1）= 0.15 × 台の近くで足を台の高さまで上げた割合 + 0.6 × 全身の重心の上がった割合 + 0.25 × 台に乗った足の数の割合。そのエピソードの最高記録を更新したときだけ与え、転倒したら、そのエピソードで得た分を取り消す。重心の高さは、「手か足が台の上に 0.1 秒以上触れ続けている」かつ「胴体の上下の速さが 0.8 m/s 未満」のときだけ数える（跳び上がった一瞬の高さを数えないため）。
- **台の高さのカリキュラム**：0.1 m（v6 までは 0.2 m）から 1.0 m まで 0.05 m 刻み。最初は 0.1〜0.3 m からランダムに始める。登れたら次の挑戦で台を高くし、ほとんど進めなかったら低くする。
- **補助の力**：手か足が台の上に触れている間だけ、腰を上向きに支える（最初は体重の 40%）。最初の 1500 イテレーションで 0 まで下げる。
- **途中の姿勢から始める**（v5、`--replay`）：以前の方策が到達した「片足を台にかけた」「台の上に立った」姿勢を `locomotion/climb_start_states.pt` に保存しておき、エピソードの 3 割をそこから始める。始めた時点の到達度を基準にするので、何もしないで報酬が出ることはない。台の上から始めた場合は最初から「登れた」扱いで、台から降りると失敗になる。姿勢は `g1_climb_collect_states.py` で集め直せる。
- **重心の前進**（v7）：到達度に「全身の重心が台の上へ前進した割合」（台の正面の 0.3 m 手前から、台の上 0.2 m まで）を加えた。重心の高さと同じく、台に触れ続けていて跳んでいないときだけ数える。v7 の到達度の重みは、足を上げた高さ 0.1・重心の高さ 0.5・台に乗った足の数 0.2・重心の前進 0.2。
- **跳んだら失敗**（v6）：一度床か台に足をついた後、体のどこも触れていない状態が 0.06 秒（3 ステップ）以上続いたら転倒と同じ扱いで終了する。常にどこかを接地させたまま登るしかなくなり、高い台では手やひざを使う必要が出る。
- **向きのペナルティ**（v6・v7 では無効、v8 で有効）：胴体（腰）の向きが台の方向から 90°（1.57 rad）以上回ると、はみ出した角度の 2 乗 × 2 を毎秒減点。90° までは減点しないので、横向きになって脚を台に掛ける登り方は許す。
- **両手で体を支える報酬**（v8）：0.6 m 以上の台で、少なくとも片足がまだ床についている間に両手を台の上についたら、1 エピソードに一度だけ 5 点。「手をついてから足を上げる」順番を促す。
- **学習済みモデルから始める**（v8、`--init-from 実験名:イテレーション`）：別の実験のモデルを読み込み、今の設定（報酬など）で学習を続ける。補助の力は最初から 0。v8b からは、最初の台の高さを全段階（0.1〜1.0 m）からランダムに選ぶ。
- **回転の速さのペナルティ**（v9）：体の向きを変える速さ（鉛直軸まわりの角速度）の 2 乗 × 0.3 を毎秒減点。向きそのものではなく、くるっと回る動きを抑える。
- **台の高さの上限の変更**（v9b、`--height-max`）：カリキュラムの上限を 1.0 m から変える。
- **低い台の復習**（v8b）：エピソードの 2 割は、段階と関係なく 0.1〜1.0 m のランダムな高さで練習する（段階の更新には使わない）。

**学習中に TensorBoard で見る項目**

| 項目 | 意味 |
|---|---|
| `Curriculum/mean_height` | 全環境の台の高さの平均。上がっていけば、高い台に登れるようになっている |
| `Curriculum/success_rate` | 登り切れたエピソードの割合（移動平均） |
| `Curriculum/assist` | 補助の力の強さ（体重に対する割合） |
| `Train/mean_episode_length` | 転ばずに続いたステップ数（最大 500 = 10 秒） |
| `Episode/rew_on_top` | 台の上に立ち続けている報酬。登った後に台の上で安定していれば大きくなる |
| `Check/progress_gain_while_jumping` | 到達度の更新のうち、跳んでいる最中に起きた割合。大きいと「跳んで稼ぐ」抜け道を使っている |

### 4.6 G1（ヒューマノイド）：はしご登り

23 関節版の G1 が、傾いたはしごを手と足を使って登ります。台へのよじ登りでは脚だけで登れてしまい手を使わなかったため、「手を使わないと物理的に登れない」タスクとして作りました。はしごが垂直に近いほど、手で体をはしごに引きつけないと後ろに倒れます。

**学習**

```powershell
uv run python locomotion/g1_ladder_train.py                                    # 4096 体 × 3000 イテレーション
uv run python locomotion/g1_ladder_train.py --resume 2999 --max-iterations 1000  # 続きを学習する
```

既定の実験名は `g1-ladder-v4` です（以前の版は `g1-ladder`・`g1-ladder-v2`・`g1-ladder-v3`）。オプションはよじ登りと同じです（`-e`・`-b`・`--max-iterations`・`--resume`・`--init-from`・`--seed`・`--cpu`）。

**再生・評価**

```powershell
uv run python locomotion/g1_ladder_eval.py                         # 最新のチェックポイントで、傾き 75° のはしごに挑戦
uv run python locomotion/g1_ladder_eval.py --angle 90              # 傾きを変える（学習は 70〜90°）
uv run python locomotion/g1_ladder_eval.py --no-viewer --trials 20 --angle 75   # 画面なしで 20 回挑戦し、成功率を表示
uv run python locomotion/g1_ladder_eval.py --record --angle 75     # 録画する
```

1 回の挑戦は最大 15 秒です。キー操作はよじ登りと同じです（Enter：開始・一時停止、Backspace：はしごの手前に戻す）。

**はしごと学習の仕組み（要点）**

- **はしご**：横棒 8 本。はしごに沿った間隔 0.25 m、一番下の段は根元から 0.25 m、長さ 0.6 m、太さ 4 cm 角。横棒は 1 本ずつ別の物体で、はしごの傾きに合わせて位置だけを変える（Genesis では、固定した物体を環境ごとに傾けられないため）。支柱は再生時だけ見た目として置く（衝突しない）。
- **握る動作（簡略化）**：G1（23 関節版）の手には指がなく、横棒を握れない。そこで行動に左右の手の「握る」指令を 2 つ加え（関節 23 + 2 = 25）、手のひらが横棒の中心線から 7 cm 以内にあるときに指令を出すと、手のひらをその位置にばねで引きつける（3000 N/m）。力には上限（片手 250 N、体重の約 8 割）があり、手が 12 cm 以上ずれると滑って外れたとみなす。指令をやめると離す。
- **成功**：両足が下から 3 段目（はしごに沿って 0.75 m）以上の横棒に乗り、少なくとも片手で握っている。その後も留まっている間、毎秒 10 の報酬。
- **進み具合の報酬**：到達度（0〜1）= 0.05 × 横棒への手の近さ + 0.2 × 握った手の高さ + 0.5 × 全身の重心の上がった割合 + 0.25 × 横棒に乗った足の高さ。最高記録を更新したときだけ与え、転倒したら取り消す（よじ登りと同じ考え方）。
- **その他の報酬**：高い段（0.7 m 以上）の横棒を初めて握ったとき片手ごとに 2 点。握力の上限に近い力で引きつけ続けるとペナルティ（腕だけでぶら下がるより、足で体重を支えることを促す）。
- **はしごの傾きのカリキュラム**：70°（v3 までは 60°）から 90°（垂直）まで 2.5° 刻み。最初は 70〜75°。登れたら急に、ほとんど進めなかったら緩やかにする。エピソードの 2 割はランダムな傾きで練習する（緩やかなはしごの登り方を忘れないように）。
- **ぶら下がった姿勢から始める**（v3、逆向きのカリキュラム）：エピソードの 3 割は、体をはしごと平行に傾け、腕を上げて下から 6〜8 段目を両手で握った姿勢から始める（足は床から浮くか、床すれすれ）。始めた時点の到達度を基準にするので、何もしないで報酬は出ない。傾きの段階の更新には使わない。
- **床に立って握った姿勢から始める**（v4）：さらにエピソードの一部（残りの 25%）は、床に立ったまま腕を前に上げ、肩より少し上の段を両手で握った姿勢から始める（足がはしごの下に入ってしまう 75° 前後より緩やかなはしごでは使わない）。床からはしごへ移る練習。
- **補助の力**：はしごに手か足が掛かっている間、腰を上向きに支える（最初は体重の 40%、1500 イテレーションで 0）。
- **転倒**：腰が 0.4 m より低い、大きく傾いた（後ろに 0.8 rad 以上など）、体のどこも触れず握ってもいない状態が 0.1 秒続いた（跳躍）、はしごの下にもぐり込んだ（足がはしごの面より 5 cm 以上向こう側、または腰がはしごの面より向こう側。v2）。
- **もたれかかりのペナルティ**（v2）：手足以外（胴体・腰・脚・腕）がはしごや床を押す力（体重比）× 5 を毎秒減点。
- **PPO の設定**：`entropy_coef` は 0.005（よじ登りの 0.01 では行動のばらつきが増え続け、はしご v1 の 0.003 では早く小さくなりすぎた）。

**学習中に TensorBoard で見る項目**

| 項目 | 意味 |
|---|---|
| `Curriculum/mean_angle` | 全環境のはしごの傾きの平均 [deg]。上がっていけば、急なはしごを登れるようになっている |
| `Curriculum/success_rate` | 目標の段まで登れたエピソードの割合（移動平均） |
| `Episode/rew_first_grip` | 高い段の横棒を握った回数に比例。手を使い始めたかが分かる |

| `Policy/mean_std` | 行動のばらつき。増え続けるなら精密な動きを覚えられていない |

## 8. これまでの結果の記録

### Go2：数式による歩行（`examples/go2_trot.py`）

### G1：強化学習（`locomotion/g1_train.py`）

学習：4096 体、1000 イテレーション → `--resume 999` で 2000 イテレーション追加（計 2999 回）。

| 評価 | model_999 | model_2998（最新） |
|---|---|---|
| 前進 0.5 m/s の平均速度（20 秒） | 0.53 m/s | 0.47 m/s |
| 前進・後退の様子 | ほぼ差なし | ほぼ差なし |
| 前進 0.5 m/s ＋ 旋回 0.5 rad/s（20 秒）の最終状態 | x=−0.50, y=+2.15 m, 向き −166 度 | x=−0.65, y=+1.80 m, 向き −146 度 |

- 旋回の理想（半径 1 m の円）は x=−0.54, y=+1.84 m, 向き −147 度。最新モデルはほぼ理想どおりで、model_999 は旋回が約 3% 遅く、向きが 19 度ずれていた。
- 1000 イテレーションの時点で、転倒せず小さな歩幅で前進できた。ただし、少しよろよろし、旋回 0 の指令でも少しずつ左に曲がった（→ 再生スクリプトに向きの自動補正を追加）。
- 追加学習の効果は、まっすぐ歩くことよりも「前進しながら旋回する」ような組み合わせの指令への追従に表れた。

### G1：台へのよじ登り（`locomotion/g1_climb_train.py`）

**1 回目（`g1-climb`、4096 体 × 3000 イテレーション）**

- 学習の最終値：`Curriculum/success_rate` 0.86、`Curriculum/mean_height` 0.93 m、`Train/mean_episode_length` 427。
- 評価では 0.6 / 0.8 / 1.0 m の台に 10 回中 10 回、約 1 秒で登れた。
- ただし実際の動きは「片足を台の高さまで蹴り上げて引っ掛け、腰を台の上 0.9 m まで跳び上がらせて飛び乗る → 台の上で跳ね続ける → 台から後ろに飛び降りる」という、手を使わない跳躍だった。台の上に立ち続けられた回は 0。
- 教訓：「台の上に一瞬でも立てたら成功」という判定だと、跳び乗る動きが一番早く報酬を得られる。また、床にしゃがんだ姿勢は「転倒」と判定されないため、評価の「台の上にいた」の集計も誤っていた（修正済み）。

**2 回目（`g1-climb-v2`）で変えた点**

- 体のどこも床や台に触れていない（跳んでいる）間のペナルティ、胴体の上下の速さのペナルティ、強すぎる衝撃へのペナルティを強化
- 台に登った後で台から降りたら転倒と同じ扱いにし、台の上に立ち続ける報酬を 2 倍（毎秒 10）に
- 0.5 m 以上の台で、手が初めて台の上に触れたときに小さな報酬（片手ごとに一度だけ）

**2 回目（`g1-climb-v2`、1500 イテレーションで中止）の結果**

- `success_rate` は 0 のままで、台の高さも 0.2 m から上がらなかった。
- 動き：0.2 m の段差に**片足だけ**乗せ、もう片方の足を床に残して体を後ろにのけぞらせ、その姿勢で 10 秒間踏ん張る。跳躍へのペナルティで近道がふさがれ、「転ばずにいる」報酬を得ながら何もしないのが一番安全になった。また、片足で跳ねた一瞬の腰の高さが到達度に数えられていた。

**3 回目（`g1-climb-v3`）で変えた点**

- 到達度を「全身の重心の高さ」中心にした（上記「進み具合の報酬」参照）。足だけ高く上げても、片足で踏ん張っても、跳んだ一瞬でも得をしない。
- 片足が台の上にあるとき、もう一方の足を台の高さに近づけるほど報酬。後ろへののけぞりにペナルティ。「転ばずにいる」報酬は半分に。
- 確認：1 回目の跳躍する方策を v3 の判定で測ると、重心の分は着地して落ち着いた後にだけ数えられ、台から降りると全額取り消された。v2 のモデルからの追加学習（CPU）でも、跳んでいる最中の到達度の更新は 0.02% だった。

**3 回目（`g1-climb-v3`、1000 イテレーションで中止）の結果**

- 到達度の報酬が最初から最後まで 0。ロボットは台の手前でしゃがんだまま何もしなかった。
- 原因：「足を台の高さまで上げた」を到達度から外したため、足が台に乗るまで報酬が一切出ず、台に近づく理由がなかった。

**4 回目（`g1-climb-v4`）で変えた点**

- 「台の近くで足を台の高さまで上げた割合」を重み 0.15 で到達度に戻した。最初の手がかりになり、重みが小さいので足を蹴り上げるだけではあまり得をしない。
- 確認：CPU で一から学習させると、最初の 100 イテレーションで到達度の報酬が 0 から上がり始めた。

**4 回目（`g1-climb-v4`、800 イテレーションで中止）の結果**

- `success_rate` 0、`mean_height` 0.2 m のまま。`progress_gain_while_jumping` は約 0.015 で、跳んで稼ぐ動きは出ていない。
- CPU での同じ設定の学習では、片足を台に乗せたまま体を起こして立ち、その後バランスを崩す動き。v2 と同じ「片足の段階」で止まっている。

**5 回目（`g1-climb-v5`）で変えた点**

- 報酬は v4 のまま。加えて、エピソードの 3 割を「途中の姿勢」から始める（逆向きのカリキュラム）。姿勢は 794 個：v1 の方策から 0.5〜1.0 m の台で「片足を台にかけた」「台の上に立った」姿勢 494 個、v2 の方策から 0.2・0.25 m の台で「片足を台にかけた」姿勢 300 個。
- 狙い：片足の段階から体を引き上げる動きと、台の上で安定して立ち続ける動きを、直接練習させる。

**5 回目（`g1-climb-v5`、4096 体 × 約 3000 イテレーション）の結果**

- 1100 イテレーションを過ぎたころから `success_rate` が 0.6 を超え、台の高さのカリキュラムも約 0.93 m まで上がった。
- 評価では 0.4 m・0.6 m の台に 10 回中 10 回登り、すべて時間切れまで台の上に立ち続けた。約 0.93 m の台でも同様。台の上ではほとんど静止している。
- ただし動きは**足だけで跳び乗る**もので、跳ぶときに体を水平面内で約 180° 回転させる。手は使っていない。
- 考察：シミュレーションではモーターの出力の上限（回転が速いほどトルクが落ちる特性）を再現していないため、脚の跳躍力が実機より強く、跳び乗るのが常に一番簡単な解になる。
- 課題デモの「保険」として、v5 の動画を先に録画しておく（`uv run python locomotion/g1_climb_eval.py -e g1-climb-v5 --height 0.6 --record`）。

**6 回目（`g1-climb-v6`）で変えた点**

- 跳ぶこと自体を失敗にした（上記「跳んだら失敗」）。v5 までは跳ぶと点数が減るだけだったので、減点より得点が大きければ跳んでいた。
- 向きのペナルティも用意したが、無効（重み 0）で学習する。v5 の 180° 回転は空中で回っていたので、跳躍を失敗にすれば起きない。また、横向きになって片ひざや脚を台に掛ける登り方を妨げるおそれがある。
- 確認：v5 の跳び乗る方策を v6 の判定で動かすと、0.6 m の台で 3 回とも跳んだ時点で「失敗（転倒）」になった。CPU での短い学習でもエラーは出ず、エピソードの長さは学習につれて伸びた。

**6 回目（`g1-climb-v6`、1300 イテレーションで中止）の結果**

- `success_rate` はほぼ 0、`mean_height` は 0.2 m のまま。`mean_episode_length` は約 290 まで伸びた（跳ばずに転ばない動きは覚えた）。
- 動き：0.2 m の台では、時間の約 9 割、片足だけを台に乗せ、深くしゃがんだ姿勢（重心約 0.51 m）で踏ん張る。両足が台に乗ったことは一度もない。腰は台の手前のふちに留まる。0.4 m の台では時々手を台につくが、登れずに転倒する。
- 考察：v2・v4 と同じ「片足の段階」で止まった。v5 はここを跳び乗りで抜けていたが、v6 では跳べない。台の上の足に体重を移し、重心を台の上へ運んでから後ろ足を引き上げる「踏み上がり」が必要だが、重心を前へ運ぶことに報酬がなく、0.2 m の台では最初からこの動きを見つけるのが難しい。
- 注意：このときの学習では、PC 上の `g1_climb_train.py` が向きのペナルティを無効にする前の版に戻っていたため、向きのペナルティ（-2.0）が有効だった。減点は 1 エピソードあたり約 -0.03 と小さく、停滞の原因ではない。

**7 回目（`g1-climb-v7`）で変えた点**

- 台の高さのカリキュラムの下限を 0.2 m から 0.1 m に下げた。0.1 m なら歩いて乗れるので、両足で台に乗る成功を経験しながら、少しずつ高さを上げていける。
- 到達度に「重心が台の上へ前進した割合」を加えた（上記「重心の前進」）。片足を台に乗せたまま台の手前で踏ん張り続けても、得をしなくなる。
- 向きのペナルティは無効（重み 0）。跳んだら失敗にする仕組みは v6 のまま。

**7 回目（`g1-climb-v7`、4096 体 × 3000 イテレーション）の結果**

- 600 イテレーションまでは 0.1 m の台にも両足で乗れなかった（片足をかけて約 1 秒後に横に倒れる）。750 イテレーション頃に 0.1 m の台に両足で乗れるようになり、そこから台の高さのカリキュラムが一気に上がった（1000 イテレーションで平均 0.83 m、最大 1.0 m、`success_rate` 約 0.55）。
- 動き：跳ばずに、片足を台にかけて約 0.8 秒かけて体を引き上げる「踏み上がり」で、0.6 m・0.9 m の台に登る。体のどこかが常に床か台に触れている。台の上ではだいたい静止しているが、たまにバランスを崩して落ちる。
- ただし手は使わず、体の向きを水平面内で約 180° 回転させながら登る（接地したまま回っているので、跳躍の禁止では防げなかった）。
- 行動のばらつき（`Policy/mean_std`）は学習中ずっと増え続けた（2.2〜2.5。歩行の学習では 0.8 から 0.55 に下がる）。報酬がまばらで、エントロピー報酬（`entropy_coef` 0.01）が勝っているためと考えられる。今後の改善候補：`entropy_coef` を 0.001 に、`init_std` を 0.8 に。

**腕の力についての見積もり**

- 最大トルクは、ひざ 139 Nm・股関節 88 Nm に対し、肩・ひじは 25 Nm。体重 32.1 kg、上腕約 0.20 m、前腕約 0.15 m。
- 足を床から離し、腕だけで体を引き上げるのはほぼ無理：ひじを 90° 曲げた引き上げでひじに約 24 Nm（上限ぎりぎり）、上腕が水平になる切り替えの局面で肩に約 31 Nm（上限超え）が、止まった状態で釣り合わせるだけで必要。
- 腕を伸ばして台を押し、体重の一部を支えたりバランスを取ったりすることはできる。したがって、目指せる動きは「台に手をついて支えながら、脚で踏み上がる」。

**8 回目（`g1-climb-v8`）で変えた点**

- v7 の学習済みモデル（model_2999）から、1000 イテレーション追加で学習する（`--init-from`）。
- 向きのペナルティを有効に（90° までは減点なし）。
- 両手で体を支える報酬（5 点、一度だけ）を追加。

**8 回目（`g1-climb-v8`、700 イテレーションで中止）の結果**

- 学習を始めた直後から `success_rate` がほぼ 0 になり、台の高さも 0.1 m まで下がったまま戻らなかった。
- 原因：v7 の最終モデルが、低い台に登れなくなっていた（0.1・0.2 m では成功 0、0.4 m 以上では登れる）。v7 は学習の終盤、ほぼすべての環境が 0.8〜1.0 m の台を練習していたため、低い台の登り方を忘れていた。v8 は台の高さのカリキュラムを 0.1〜0.3 m から始めたので、すべて失敗して高さが下がり続けた。報酬の変更（向き・手）が原因ではない。
- 教訓：カリキュラムの最上段に到達した後も、低い段階を一定の割合で練習させる必要がある（v7 の 0.6 m・0.9 m の評価は問題ないが、低い台では使えない）。

**8 回目のやり直し（`g1-climb-v8b`）で変えた点**

- 低い台の復習（エピソードの 2 割はランダムな高さ）を追加。
- 学習済みモデルから始めるときは、最初の台の高さを全段階からランダムに選ぶ。
- 報酬は v8 と同じ（向きのペナルティ、両手で体を支える報酬）。

**8 回目のやり直し（`g1-climb-v8b`、v7 の model_2999 から 1000 イテレーション）の結果**

- 低い台の復習が効き、学習はすぐに立ち直った：100 イテレーションで `success_rate` 0.95、最後は 0.97、台の高さの平均 0.93 m。
- 動き（0.02 秒ごとに記録）：0.3 秒で正面を向いたまま片足を台にかけ、0.4〜1.1 秒に台の上の足を軸に左回りに約 250° 回りながら体を引き上げ、最後は横向き（台の方向から約 -90°〜-110°）で台の上に立って静止する。跳ばずに登り、台の上でも安定している（予備のデモとして録画済み）。
- 手は一度も台につかなかった（`rew_hands_support` は最初から最後まで 0）。脚だけで登れるので、手をつく動きを偶然見つける機会がない。
- 向きのペナルティ（90° まで減点なし）は、最後の向きが 90° 前後に収まり、180° 付近を通るのは約 0.3 秒だけなので、ほとんど効かなかった。

**9 回目（`g1-climb-v9a`・`g1-climb-v9b`）で変えた点**

- どちらも v8b の学習済みモデル（model_3998）から 1000 イテレーション。
- v9a：回転の速さのペナルティ（上記）を追加。今の回り方（約 0.7 秒で 250°）だと約 -8 点。ゆっくり横を向く登り方は妨げない。
- v9b：v9a に加えて、台の高さの上限を 1.2 m に。股関節の可動範囲から見ると、脚だけで足を上げられるのは約 1.2〜1.3 m までなので、1.1〜1.2 m の台では手・ひじ・胸などを台に掛ける必要が出る（腕の力が弱いので、登れずに終わる可能性もある）。

**9 回目（`g1-climb-v9a`・`g1-climb-v9b`）の結果**

- v9a：成功率 0.98。0.9 m の台に脚で踏み上がり、約 250° 回りながら約 1 秒で登って、横向き（約 -105°）で静止する。回転の速さへのペナルティで回る速さは少し落ちたが、回り方は変わらなかった。
- v9b：成功率 0.92、台の高さの平均 1.13 m。1.1 m・1.2 m の台にも、ほぼ脚だけで登る（最初に手が一瞬台に触れるだけ）。約 240° 回り、横向き（約 -115〜-120°）で静止。予備のデモとして録画済み。
- どちらも、両手で体を支える報酬は 0 のまま。
- 1.2 m の台を登るときの関節を測ると、股関節（前後）は最大トルク 88 Nm を出したまま 27 rad/s（速さの上限 32 rad/s）で回り、出力は約 2,200 W に達していた。本物のモーターは速く回るほど出せるトルクが下がる（27 rad/s では約 14 Nm）が、シミュレーションではどんな速さでも最大トルクが出せる。このため脚の瞬発力が実機よりはるかに大きく、脚だけで登れてしまう。

**よじ登りのタスクのまとめ**

- 跳ばずに脚で踏み上がり、0.9 m（v8b）・1.2 m（v9b）の台に登って静止する動きまでは学習できた。
- 手を使わせることはできなかった。脚だけで登れる道が残っている限り、報酬を工夫しても脚だけの解に流れやすい。また、腕の力（URDF では 25 Nm）が脚よりずっと弱く、手と足の両方を使わないと登れない台の高さの範囲は、あったとしても狭いと考えられる。
- そこで、手を使わないと物理的に成功できないタスクとして、はしご登り（4.6 節）に切り替えた。

**教訓（報酬設計の難しさ）**

- 手がかりの報酬を入れると、それを稼ぐ抜け道（飛びつく・蹴り上げる・跳ぶ・片足で踏ん張る）を覚える。外しすぎると、何もしないのが一番安全になる。その間の適切な加減を、実際の動きを見ながら探る必要がある。

### G1：はしご登り（`locomotion/g1_ladder_train.py`）

**1 回目（`g1-ladder`、800 イテレーションで中止）**

- 設定：4.6 節の仕組みから、はしごの下へのもぐり込みの判定ともたれかかりのペナルティを除いたもの。`entropy_coef` 0.003、`alive` 0.5。
- 結果：`success_rate` 0、はしごの傾きは 60° のまま。エピソードはほぼすべて 15 秒の時間切れまで続いた（転ばない）。行動のばらつきは 0.39 まで下がった。
- 動き（60° のはしご）：はしごに向かって歩き、胸をはしごにもたれかけ（胴体がはしごを体重ほどの力で押していた）、片手で下から 3 段目の横棒をときどき握ったまま動かない。足は床のまま。転ばずにいる報酬と、手の近さ・握った高さの到達度だけを得て、安全にじっとしているのが一番得になっていた。

**2 回目（`g1-ladder-v2`）で変えた点**

- もたれかかりのペナルティを追加（手足以外がはしごや床を押す力に比例）。1 回目の動きだと 15 秒で約 -20。
- はしごの下にもぐり込んだら失敗に。
- `alive` を 0.5 → 0.2、`entropy_coef` を 0.003 → 0.005 に。

**2 回目（`g1-ladder-v2`、500 イテレーションで中止）**

- 結果：`success_rate` 0、傾きは 60° のまま、ほぼ全エピソードが時間切れまで続く。行動のばらつきは 0.64 で保てた。もたれかかりは減った（`rew_body_contact` は小さい）。
- 動き（60° のはしご）：はしごに歩み寄り、下から 3 段目（高さ約 0.7 m）を両手で握り、足を後ろ（はしごの 0.5 m 手前）に残して前かがみになったまま動かない。握った手で体重の一部を支えられるので、これが安全な休み方になった。足を横棒に乗せる動きは一度も見つからなかった。
- 考察：v1・v2 とも、足を横棒に乗せたり体を上げたりする経験が一度もないまま、「転ばずにじっとする」解に落ち着いている。台へのよじ登りの v5 で効いた「ゴールに近い状態から練習させる」方法を使う。

**3 回目（`g1-ladder-v3`）で変えた点**

- エピソードの 3 割を、はしごの高い段を両手で握ってぶら下がった姿勢から始める（上記「ぶら下がった姿勢から始める」）。足を横棒に乗せて体を押し上げる経験を、最初から積ませる。

**3 回目（`g1-ladder-v3`、600 イテレーションで中止）**

- 結果：`rew_success` が 0 から約 0.05 に上がった（ぶら下がった姿勢から始めた回で成功が出始めた）。`rew_on_target` も 0 → 0.5〜0.7。床から始めた回の `success_rate` は 0 のまま、傾きは 60° のまま。行動のばらつきは 0.78。
- 動き（各 16 体、ノイズなしで 15 秒）：
  - ぶら下がった姿勢から、75° のはしご：足を横棒に乗せ、目標の段まで上がって握り続ける回が出た（成功 4 回、目標の段にいる時間の割合 14%）。
  - ぶら下がった姿勢から、60° のはしご：足を横棒に乗せる（時間の半分）が、目標の段には届かない。
  - ぶら下がった姿勢から、90° のはしご：時々手を握り直して下の段へ移るが、落ちることもある。
  - 床から、60° のはしご：横棒を一度も握らないまま、約 2.5 秒で毎回転倒する。
- 考察：はしごの上での動き（足を乗せて体を上げる）は覚え始めた。床からはしごに取り付く段階がつながっていない。また 60° では横棒が前に遠く、手で握りにくい。

**4 回目（`g1-ladder-v4`）で変えた点**

- v3 の学習済みモデル（model_600 など、中止した時点の最新）から学習を続ける（`--init-from`）。補助の力は、読み込んだイテレーションの位置から続けて下げる（v4 から。以前は最初から 0）。
- 床に立って握った姿勢から始めるエピソードを追加（上記「床に立って握った姿勢から始める」）。
- はしごの傾きの範囲を 70〜90° に（60° をやめた）。

### 次に試すとよいこと（候補）

- 歩幅を大きく・動きを滑らかにしたい場合は、報酬の配分（`g1_train.py` の `reward_scales`）を見直す。
- 学習時から向きを指令する方式（Unitree の `heading_command`）にすると、再生時の補正なしでもまっすぐ歩ける可能性がある。

## 9. Git の運用

- ファイルの編集は Claude チャットから行い、コミットとプッシュは Visual Studio から手動で行う。
- コミットするもの：ソースコード、`pyproject.toml`・`uv.lock`・`.python-version`、`assets/`、`docs/`
- `.gitignore` で除外しているもの：`.venv/`（仮想環境）、`logs/`（学習結果）、`videos/`（録画）、`.vs/`（Visual Studio のキャッシュ）、`.serena/`
- 学習結果（`logs/`）は Git に含めないので、残したいチェックポイントは別の場所にバックアップする。
- 間違えてコミットした場合（プッシュ前）：Visual Studio の「Git リポジトリ」で 1 つ前のコミットを右クリック →「リセット」→「変更を保持 (--mixed)」。コマンドなら `git reset HEAD~1`。「変更を破棄 (--hard)」はファイルの変更まで消えるので使わない。

## 10. トラブルシューティング

| 症状 | 原因と対処 |
|---|---|
| `FileNotFoundError: ... model_1000.pt` | 1000 イテレーション学習した場合の最後は `model_999.pt`。G1 は `--ckpt` を省略すれば最新を自動で選ぶ |
| `Genesis hasn't been initialized` | スクリプトの最初で `gs.init()` を呼んでいない |
| キーを押しても反応しない | ビューアーのウィンドウをクリックして選択してから押す |
| `uv python pin` で `incompatible with the project requires-python` | `pyproject.toml` の `requires-python` と矛盾している。現在は `>=3.12,<3.14` |
| `torch.cuda.is_available()` が `False` | CPU 版の PyTorch が入っている、またはドライバーが古い。`nvidia-smi` で確認し、`pyproject.toml` の PyTorch の取得先を見直す |
| PowerShell で `Activate.ps1` などのスクリプトが実行できない | `uv run` を使えば有効化は不要。必要なら `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` |
